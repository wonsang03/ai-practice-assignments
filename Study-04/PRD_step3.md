# PRD 3단계 — 사용자 프로필과 레시피 저장

> 프로젝트: 냉장고를 부탁해 (Study-04) · 상태: **미구현 (계획)**

## 1. 목표

사용자가 로그인해 마음에 드는 레시피를 저장하고, 대시보드에서 저장한 레시피와 사용 통계를 본다.
실제 데이터베이스·배포 없이 로컬에서 동작하는 **프로토타입**이다.

## 2. 범위

| 포함 | 제외 |
| --- | --- |
| 로그인 화면, 데모 계정 로그인, 간단한 회원가입 | 실제 인증 서비스·소셜 로그인 |
| 레시피 [저장] / 삭제, [나의 레시피] 탭 | 클라우드 DB, 여러 기기 동기화 |
| 대시보드: 저장 수, 요리 횟수, 자주 쓰는 재료 | 배포·도메인·HTTPS 설정 |
| 프로필(닉네임, 선호 요리 종류) 편집 | 비밀번호 찾기·이메일 인증 |

## 3. 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| F3-1 | 앱을 열면 로그인 화면이 먼저 나온다. [데모 계정으로 시작] 버튼으로 바로 들어갈 수 있다. |
| F3-2 | 회원가입은 아이디·비밀번호·닉네임만 받는다. 비밀번호는 평문으로 저장하지 않고 솔트를 붙인 해시(`hashlib.pbkdf2_hmac`)로 저장한다. |
| F3-3 | 2단계에서 생성한 레시피 옆에 [저장] 버튼을 둔다. 같은 레시피를 두 번 저장하지 않는다. |
| F3-4 | [나의 레시피] 탭에서 저장한 레시피를 펼쳐 보고, 삭제하고, "만들어 봤어요"를 누를 수 있다(요리 횟수 +1). |
| F3-5 | 대시보드에 저장한 레시피 수, 요리 횟수 합계, 자주 쓰는 재료 상위 5개, 최근 저장 레시피를 보여 준다. |
| F3-6 | 프로필에서 닉네임과 선호 요리 종류를 바꿀 수 있고, 선호 요리 종류는 2단계의 기본값이 된다. |
| F3-7 | 데이터는 `data/users.json`, `data/recipes.json`에 저장한다(`data/`는 git에서 제외). |

## 4. 화면

```
[로그인]  아이디 [____]  비밀번호 [____]  [로그인]  [회원가입]  [데모 계정으로 시작]

사이드바: 👤 닉네임 · [대시보드] [재료 인식] [레시피 생성] [나의 레시피] [프로필] · [로그아웃]

[대시보드]
 저장한 레시피 5 | 요리 횟수 12 | 자주 쓰는 재료: 계란, 대파, 양파 …
 최근 저장: 대파 계란말이, 김치볶음밥 …
```

## 5. 데이터·API 사양

- 외부 API는 1·2단계와 같다(새 API 없음).
- `users.json`: `{"<아이디>": {"nickname": "…", "salt": "…", "hash": "…", "favorite_cuisine": "한식"}}`
- `recipes.json`: `{"<아이디>": [{"id": "…", "saved_at": "ISO 시각", "cooked": 0, "recipe": { 2단계 레시피 객체 }}]}`
- 저장 로직(`storage.py`)은 화면과 분리해 테스트할 수 있게 한다. 파일 쓰기는 임시 파일에 쓴 뒤 바꿔치기해 중간에 깨지지 않게 한다.

## 6. 오류 처리

- 아이디 중복, 빈 입력, 비밀번호 불일치는 입력란 아래에 안내한다(어느 쪽이 틀렸는지 구분하지 않고 "아이디 또는 비밀번호가 올바르지 않습니다").
- 저장 파일이 없거나 깨졌으면 빈 데이터로 시작하고, 깨진 파일은 `*.bak`으로 남긴다.
- 데모 계정 데이터는 다른 사용자와 섞이지 않게 별도 아이디(`demo`)로 저장한다.

## 7. 완료 기준

- [ ] 회원가입 → 로그아웃 → 로그인이 된다. 저장 파일에 비밀번호 평문이 없다 (단위 테스트)
- [ ] 레시피 저장·중복 방지·삭제·요리 횟수 증가 테스트 통과
- [ ] 대시보드 통계(저장 수, 요리 횟수, 자주 쓰는 재료) 계산 테스트 통과
- [ ] 깨진 JSON 파일에서 시작해도 앱이 죽지 않는다 (단위 테스트)
- [ ] 데모 계정으로 1→2→3단계를 이어서 실행해 저장·대시보드 반영을 직접 확인
- 참고: 로컬 프로토타입이므로 서버를 재시작해도 `data/` 파일은 남지만, 다른 사람은 접속할 수 없다.
